# Как устроен этот репозиторий — читать перед любой правкой

Этот файл — для любого, кто впервые открывает репозиторий: человека или ИИ
в новом чате/на другой платформе, без памяти о прошлых разговорах. Он
отвечает на три вопроса: **что где лежит**, **как это всё связано** и
**как внести и выложить изменение**. Детали конкретных шагов — в
`DEPLOY.md` (первичное развёртывание и обновление сервера построчно) и
`docs/spec.md` (что должен делать продукт). Здесь — карта, а не инструкция
по каждой команде.

---

## 1. Что это

**Доска Пи** (домен `board.school-pi.online`) — доска для совместной
работы в браузере в реальном времени: пишут пером, вставляют документы,
участник заходит по ссылке без регистрации. Продаётся по подписке —
платит тот, кто создаёт доски.

Формальное имя продукта — «Доска Пи» (это то, что должно стоять в
оферте, письмах, заголовке сайта). Стилизованное «π» вместо слова «Пи» —
только оформление конкретных мест на сайте (шапка, подвал, карточка
«Школа π» на главной), не замена имени.

Три соседних службы на одном сервере, связанные только машиной и почтой,
никаких общих таблиц или прямых вызовов между ними:

| Служба | Домен | Роль |
|---|---|---|
| Доска (этот репозиторий) | `board.school-pi.online` | сама доска |
| Главный сайт | `school-pi.online` | Flask/gunicorn, к доске не относится |
| Сервер ключей | `keys.school-pi.online` | владеет всей платёжной обвязкой; доска сама в Робокассу не ходит, см. `docs/license-server-protocol.md` |

Десктопная версия доски — отдельная программа по разовой лицензии,
не часть этого репозитория.

## 2. Структура репозитория

| Путь | Что там |
|---|---|
| `server/SchoolPiBoard.Web/` | ASP.NET Core 8 + SignalR: весь backend, один проект |
| `server/SchoolPiBoard.Web/Endpoints/` | минимальные API-эндпоинты (`/api/boards`, `/api/auth`, `/api/admin`, …) |
| `server/SchoolPiBoard.Web/Services/` | бизнес-логика (`BoardService`, `AccountService`, `SubscriptionService`, …) |
| `server/SchoolPiBoard.Web/Hubs/BoardHub.cs` | SignalR-хаб: рисование, курсоры, присутствие — всё, что происходит на холсте в реальном времени |
| `server/SchoolPiBoard.Web/Data/` | `AppDbContext`, сущности EF Core |
| `server/SchoolPiBoard.Web/Migrations/` | миграции EF Core — **пишутся вручную**, см. раздел 6 |
| `webapp/` | React + TypeScript + Vite, весь frontend |
| `webapp/src/pages/` | страницы-маршруты (`BoardsPage`, `BoardPage`, `LandingPage`, …) |
| `webapp/src/board/` | всё про сам холст: `BoardCanvas.tsx`, `useBoardHub.ts`, инструменты рисования |
| `webapp/src/components/` | общие компоненты (`Layout.tsx` — шапка/подвал/сайдшелл доски, `Modal`, `Menu`, …) |
| `webapp/src/styles/` | `schoolpi-theme.css` (токены темы, общие элементы), `board-app.css` (всё специфичное для приложения) |
| `webapp/dist/` | собранный клиент — **в git не попадает** (`.gitignore`) |
| `webapp/dist-ssr/` | результат SSR-сборки для пререндера — **в git закоммичен** (см. раздел 8, это унаследованная особенность, не сознательный выбор — не пугаться, увидев тут собранный JS) |
| `deploy/` | `schoolpiboard.service` (юнит systemd), `nginx-board.conf` (см. раздел 5 — **не зеркало живого файла**), `env.example` |
| `docs/spec.md` | полное техническое задание на продукт, по разделам и этапам |
| `docs/license-server-protocol.md` | протокол общения с сервером ключей (биллинг) |
| `.github/workflows/online-board.yml` | вся сборка и публикка релиза — см. раздел 4 |
| `DEPLOY.md` | первичное развёртывание с нуля и команды обновления, шаг за шагом |

## 3. Как всё связано на сервере (продакшен)

```
Браузер
  │  HTTPS (сертификат Let's Encrypt, продлевает certbot)
  ▼
nginx  (server_name board.school-pi.online)
  │  раздаёт статику из web/ напрямую
  │  проксирует /api/*      → 127.0.0.1:5081
  │  проксирует /api/hub/*  → 127.0.0.1:5081 (с Upgrade/Connection — вебсокет)
  ▼
systemd-служба «schoolpiboard» (пользователь boardsvc, без домашней папки и логина)
  │  ASP.NET Core процесс, слушает 127.0.0.1:5081
  ├──► PostgreSQL, своя база schoolpiboard, свой пользователь boardsvc
  ├──► Redis, номер базы 1 (backplane SignalR + присутствие на досках)
  ├──► keys.school-pi.online — по HTTP, свой общий секрет (LICENSE_SHARED_SECRET)
  └──► SMTP Яндекса — письма (подтверждение почты, восстановление пароля, чеки)
```

Всё это — **на одном сервере**, но каждый со своим пользователем/базой/
номером Redis, чтобы не пересекаться с главным сайтом и не мешать ему.

Файлы на сервере:

```
/var/www/schoolpiboard/
  .env            секреты, права 600, владелец boardsvc — состав описан в deploy/env.example
  api/            опубликованный ASP.NET Core процесс (приходит в архиве сборки)
  api/migrate     однофайловая сборка, применяющая миграции — приходит в том же архиве
  web/            собранный клиент (то, что раздаёт nginx)
```

Сервер **не имеет** ни .NET SDK, ни Node.js, ни исходников, ни git —
только готовый рантайм ASP.NET Core. Собирает всё GitHub Actions, сюда
приезжает только готовый архив.

## 4. Сборка и релиз (CI)

`.github/workflows/online-board.yml` запускается на **любой push**, если
изменились файлы под `server/**`, `webapp/**` или сам файл воркфлоу
(а также вручную, `workflow_dispatch`). **Ветка не важна** — сборка не
проверяет, с какой ветки пришёл push, и результат всегда уходит в один
и тот же релиз, независимо от того, в какой ветке шла работа.

Что делает сборка, по шагам:

1. `dotnet build` — компилирует backend. Если правка ломает сборку C#,
   упадёт здесь, с текстом ошибки в логе джобы.
2. Две проверки миграций (важны, потому что миграции пишутся вручную,
   без `dotnet ef migrations add` — см. раздел 6):
   - миграции вообще находятся (`dotnet ef migrations list`);
   - модель и миграции описывают одну и ту же схему
     (`dotnet ef migrations has-pending-model-changes`). Если модель
     (сущности + `AppDbContext.OnModelCreating`) поправили, а миграцию
     и `AppDbContextModelSnapshot.cs` — не поправили или поправили не в
     тон, сборка станет красной именно здесь.
3. `dotnet publish` — собирает сам процесс API.
4. `dotnet ef migrations bundle` — собирает `migrate`, однофайловый
   исполняемый файл для применения миграций на сервере (SDK там нет).
5. `npm ci && npm run build` в `webapp/` — собирает клиента (`tsc`,
   `vite build`, SSR-сборка, пререндер статических страниц, sitemap).
6. Всё упаковывается в `online-board.tar.gz` (`api/` + `web/` внутри).
7. Архив публикуется как ассет **одного и того же** релиза с фиксированным
   тегом `online-board-latest` (заменяется каждый раз, `--clobber`) —
   поэтому ссылка на скачивание никогда не меняется:

   ```
   https://github.com/pootymoty/schoolpiboard_online/releases/download/online-board-latest/online-board.tar.gz
   ```

Проверить статус конкретного запуска — в вебе на вкладке Actions
репозитория, или через GitHub API/CLI по SHA коммита.

## 5. nginx — важная оговорка

`deploy/nginx-board.conf` в репозитории — это ориентир, **не зеркало**
живого файла на сервере. На сервере в `/etc/nginx/sites-available/schoolpiboard`
дополнительно есть блок, который дописал (и продолжает обслуживать) certbot
при выпуске SSL-сертификата — строки с комментарием `# managed by Certbot`,
второй `server {}` для редиректа с 80 на 443. Этого блока нет и не должно
быть в репозитории: сертификат на этой машине, конфиг для него генерирует
certbot сам.

**Перед любой правкой этого конфига на сервере — сначала посмотреть, что
там реально лежит:**

```bash
cat /etc/nginx/sites-available/schoolpiboard
```

и вносить точечную правку в то, что увидели, а не перезаписывать файл
версией из репозитория целиком — так легко случайно стереть блок
сертификата и уронить HTTPS. Также сам конфиг **не входит в архив
сборки** — правка `deploy/nginx-board.conf` в репозитории требует
отдельного ручного шага на сервере (`nginx -t`, затем `systemctl reload
nginx`), автоматический деплой (раздел 7) его не касается.

## 6. Миграции EF Core — пишутся вручную

В обычном проекте миграцию создаёт `dotnet ef migrations add ...`. В
среде, где готовятся правки для этого репозитория, нет .NET SDK — миграции
и `Migrations/AppDbContextModelSnapshot.cs` **пишутся руками**, по образцу
уже существующих файлов в `Migrations/`. Правило:

1. Меняешь сущность (`Data/Entities/*.cs`) и её конфигурацию в
   `AppDbContext.OnModelCreating`.
2. Пишешь новый файл миграции `Migrations/{timestamp}_{Name}.cs` (timestamp
   строго больше последнего существующего) — по образцу соседних файлов
   в этой папке, тот же стиль вызовов `migrationBuilder.CreateTable`/
   `AddColumn`/`CreateIndex`.
3. Вручную дописываешь тот же набор изменений в
   `Migrations/AppDbContextModelSnapshot.cs` — он должен описывать финальную
   схему в точности как её теперь описывает модель. Это тот файл, который
   сверяет шаг 2 сборки (раздел 4): малейшее расхождение — красная сборка.
4. Настоящая проверка — не локальная (компилятора и `dotnet ef` нет),
   а через CI: пушишь, смотришь статус запуска в Actions. Если сборка
   красная на шаге проверки миграций — значит модель и снэпшот
   разошлись, надо смотреть diff внимательно.

## 7. Как выложить изменение на сервер (обновление)

Короткая версия — команды. Полная версия с пояснениями к каждой — раздел
«Обновление» в `DEPLOY.md`.

```bash
curl -L -o /tmp/online-board.tar.gz https://github.com/pootymoty/schoolpiboard_online/releases/download/online-board-latest/online-board.tar.gz
```

```bash
ls -lh /tmp/online-board.tar.gz
```

Архив весит около 27 МБ. Если сильно меньше — скачался не архив, а
страница ошибки (например, CDN GitHub не успел раздать файл сразу после
публикации релиза) — **не распаковывать**, скачать заново через минуту.

```bash
sudo tar -xzf /tmp/online-board.tar.gz -C /var/www/schoolpiboard
```

```bash
sudo -u boardsvc bash -c 'set -a; . /var/www/schoolpiboard/.env; set +a; export DOTNET_BUNDLE_EXTRACT_BASE_DIR=/var/www/schoolpiboard/.bundle; mkdir -p "$DOTNET_BUNDLE_EXTRACT_BASE_DIR"; /var/www/schoolpiboard/api/migrate'
```

Именно так, не короче: `/var/www/schoolpiboard/api/migrate` без
предварительной загрузки `.env` не видит `DATABASE_URL` и падает с
попыткой подключиться заглушкой пароля. `DOTNET_BUNDLE_EXTRACT_BASE_DIR`
обязателен — у `boardsvc` нет домашней папки, куда однофайловая сборка
распаковывает себя по умолчанию.

Если в этом обновлении нет новой миграции — команда просто ничего не
найдёт и завершится, это нормально, не ошибка.

```bash
sudo systemctl restart schoolpiboard
```

```bash
curl -s http://localhost:5000/api/health
```

Ожидается `{"status":"ok"}`.

**Если менялся `deploy/nginx-board.conf`** — этот файл отдельно, вручную,
с учётом раздела 5 (не перезаписывать целиком), плюс `sudo nginx -t` и
`sudo systemctl reload nginx`.

Замеченная нестыковка: исходная версия `DEPLOY.md` включает шаг
`chown -R boardsvc:boardsvc /var/www/schoolpiboard` сразу после
распаковки архива. На практике обновления этой сессии проходили без
этого шага и служба поднималась нормально — судя по всему, права внутри
самого архива уже достаточно открытые. Если после обновления служба не
стартует с ошибкой доступа — первым делом попробовать вернуть этот шаг.

## 8. Особенности фронтенда, о которых легко забыть

- **`webapp/dist-ssr/` закоммичен в git**, хотя это результат сборки —
  унаследованная особенность репозитория, не текущее сознательное
  решение. Не удалять и не «чистить» не спросив — но и не удивляться,
  если там лежит скомпилированный JS.
- Сборка (`npm run build` в `webapp/`) — это четыре шага подряд:
  `tsc --noEmit` (проверка типов) → `vite build` (клиентский бандл) →
  `vite build --ssr` (SSR-бандл для пререндера) → `node scripts/prerender.mjs`
  (раскладывает 11 статических страниц по файлам + `sitemap.xml`, см.
  `webapp/src/seo.ts` — список маршрутов, которые становятся отдельными
  HTML-файлами для поисковика).
- `VITE_API_URL` в продакшен-сборке — `/api` (относительный путь, тот же
  домен) — задаётся переменной окружения при сборке, см. шаг 5 в разделе 4.
- Компилятора C# и `dotnet ef` в песочнице, где обычно готовятся правки,
  нет — backend правится «на глаз», по образцу соседнего кода, и
  по-настоящему проверяется только сборкой в CI (раздел 4). Frontend,
  наоборот, можно и нужно проверять локально: `npx tsc --noEmit` и
  `npm run build` работают без сервера и без сети (кроме первого
  `npm ci`).

## 9. Типичный порядок работы над изменением

1. Прочитать этот файл и, если правка касается конкретной области —
   соответствующий кусок `docs/spec.md`.
2. Внести изменение в `server/` и/или `webapp/`.
3. Проверить, что получилось:
   - frontend: `cd webapp && npx tsc --noEmit && npm run build`;
   - backend: перечитать diff внимательно вручную (компилятора нет) —
     сверить сигнатуры, using-директивы, что вызываемые методы
     существуют и с той же сигнатурой.
4. Закоммитить с понятным сообщением, запушить.
5. Проверить статус сборки в GitHub Actions (раздел 4) — для backend-правок
   это единственная настоящая проверка.
6. Если сборка зелёная — выложить на сервер (раздел 7).
7. Если менялась схема базы — убедиться, что шаг применения миграций в
   выводе показал что-то, а не молчание (значит, миграция не нашлась —
   смотреть раздел 6).
